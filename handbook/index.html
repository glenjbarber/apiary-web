For operators

Vocabulary

Apiary's own terms for the containment hierarchy it manages.

Colony
The whole cluster: every Comb, and everything running on them, held together by a single Raft consensus group.
Comb
One physical FreeBSD host. A Colony can be a single standalone Comb or several Combs joined together - both are first-class.
Cell
One VM or jail. Placed on a Comb, reconciled continuously against its desired state, visible cluster-wide.

Install a Comb

From a bare FreeBSD host to an installed Comb.

apiaryctl install takes a bare FreeBSD host - configuration, certificates, and identity - from a root shell and nothing else. It changes nothing without --apply, and the useful part of its report is the list of what it decided not to overwrite, and why.

Full walkthrough: ADR-0147, Part 1.

Join a Colony

Adding a Comb to an existing Colony.

A Comb can only join while the Colony's join window is open - closed is the normal state, and a request against a closed window is refused by name. Approval requires a live join window, a matching unused entry in the root-owned authorization store, and two approvals from distinct API keys presented to distinct Combs, even when the Colony currently has one member. Raft member traffic, and manager-to-manager peer calls, run over mutually authenticated TLS by default.

Full flow: ADR-0147, ADR-0155.

Day-to-day operation

What the web UI and CLI give an operator once a Colony is up.

Cell lifecycle
Create, Stop, Start, Restart, and delete VMs and jails from the web UI; CreateVM/CreateJail and friends over the external gRPC/REST API for anything scripted.
Evidence
Automated assumption checks, a Why-Not engine, and a resilience coverage map show what is actually true about the Colony right now, and what would break it.
Replication
A VM or jail can name a replica_node_id to get real HAST-backed disk replication to another Comb - not automatic failover.
Watchgoose heartbeat
Optional per-Comb heartbeat monitoring, enabled under Machine → Operations → Watchgoose monitoring.

Runbooks: docs/runbooks.

For contributors

Architecture

Language
Go, across the entire stack.
Hypervisor
bhyve, for both VMs and jails.
Storage
ZFS, replicated node-to-node via HAST.
Consensus
A dedicated raft agent (hashicorp/raft), run as a separate process from the management daemon over a schema-defined Unix domain socket protocol.
External API
RPC-style first (CreateVM, MigrateVM, ...), with a REST translation layer on top.
Frontend
A Go backend serving a JSON API, with HTMX handling interactive elements server-side.

Repository layout

cmd/
Entry points: raftd, managerd, frontend, restshimd, apiaryctl, apiaryinstall, versioncheck.
api/
Protobuf schema: api/internalpb (internal raft socket protocol) and api/rpc (external RPC API).
internal/
Core logic, one package per feature or ADR - bhyve, jail, zfs, hast, raft, manager, restshim, frontend, and dozens more.
web/
HTML templates and static assets for the frontend, embedded into the frontend binary at build time.
docs/adr/
Architecture decision records - start here for why things are built the way they are.

Building and testing

Standard Go tooling: go build ./..., go vet ./..., go test ./.... Packages that shell out to FreeBSD-only tools (internal/zfs, internal/jail, internal/hast, internal/bhyve) skip their integration tests cleanly on a non-FreeBSD dev machine - cross-compile (GOOS=freebsd GOARCH=amd64 go test -c ./internal/<pkg>) and run the resulting binary on a FreeBSD host to exercise them for real.

Proto changes require buf (buf generate); generated .go files are committed, so this isn't needed just to build. cmd/frontend links internal/pam (cgo) for real PAM login and can't be cross-compiled from macOS - build it natively on a real FreeBSD host instead. managerd/raftd/restshimd are unaffected.
